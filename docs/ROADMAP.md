# ROADMAP

Principles:
- **Each phase has exit criteria.** Don't start the next phase until the current one's criteria are met (or the owner explicitly waives one, logged in SESSION_LOG).
- **Each phase lists "what could go wrong".** Re-read it at the start of the phase.
- **Durations are deliberately not given.** Estimating would be dishonest before ADR-001/002 and the owner's skill level (Q-002) are known.

---

## Phase 0 — Decisions & spikes (NOW)

**Goal:** Remove the biggest unknowns before writing real code.

Tasks:
1. Owner answers 🔴 questions in `OPEN_QUESTIONS.md`.
2. Accept ADR-001 (platform), 002 (stack), 003 (2D/3D), 004 (construction system), 005 (analysis tier), 006 (units), 009 (country/code), 010 (build vs extend).
3. **Spike A — wall joins:** throwaway prototype that draws walls with thickness and correctly cleans up L, T, X junctions. *(This is the #1 geometry trap in every CAD-like tool.)*
4. **Spike B — one structural rule end to end:** a hard-coded wall + opening → one rule (e.g. "opening in load-bearing wall needs a lintel") → a finding with explanation. Proves the explanation format.
5. **Spike C (only if build-vs-extend is still unclear):** try doing the same thing as a plugin for an existing tool (e.g. FreeCAD or Bonsai/BlenderBIM) for one afternoon. *(Lower priority now: the modular "Visions" idea makes building our own more justified, but a quick look at how FreeCAD workbenches are organized is still a cheap source of module-design ideas.)*
6. **Spike D — stack (added session #1):** Tauri 2 + Vue 3 + TS hello-world: SVG canvas with 500 walls (pan/zoom/drag) + a Three.js scene, built for **Windows and macOS** (ADR-027; Linux build-only, optional) via GitHub Actions. Record installer sizes, startup time, and smoothness per OS. Decides ADR-001/002.
7. **Spike E — module boundary (added session #1):** in plain TS (no UI), a tiny core + two fake modules ("architect" adds walls, "structural" adds a `structural` component and one rule) + save/load where one module is missing → data preserved. Proves MODULES.md rules 1, 3, and 4 before real code depends on them.
8. Write the first 5 validation cases (hand-calculated) in `STRUCTURAL_ANALYSIS.md` for the Brazil profile; send them to the engineer for review.
9. Create the **public repo** (ADR-014): LICENSE (Apache-2.0, generated by GitHub's license picker), README, CONTRIBUTING, CLAUDE.md, docs/. Answer Q-083 (name) first, or use a codename.
10. Decide Q-079 (rooms vs walls) before Phase 1 starts. It changes Phase 1 scope.

Exit criteria:
- [ ] All 🔴 questions answered.
- [ ] The ADRs listed above are ACCEPTED, plus ADR-019/020/022.
- [ ] Spikes A, B, D, and E done, lessons written in SESSION_LOG, and the spike code **deleted or moved to `/spikes`** (not promoted to production).

What could go wrong:
- Owner fatigue: too many questions. → Mitigation: answer in batches; every question has a default.
- Spikes quietly become the product. → Mitigation: rule above.

## Phase 1 — Architect Vision: 2D editor core (no structure yet)

**Goal:** A pleasant, reliable 2D plan editor, **built as the first module** (`module-architect`) on the internal module API (ADR-020). Includes the app shell with a Vision switcher (only one Vision available yet), i18n (pt-BR/en), and CI producing installers for all 3 OS.

Scope:
- Canvas with pan/zoom, grid, snapping (endpoints, midpoints, grid, orthogonal).
- Walls: draw, thickness, height, alignment (centre/left/right of the drawn line), auto-join.
- Openings: place on wall, slide along wall, width/height/sill height, kind (door/window/void), handing/swing for doors.
- **Room tool (Q-079 ✅, ADR-031):** draw a rectangle/polygon room → walls created, shared walls merged; rooms auto-detected from closed loops of full walls + room separators.
- **Wall kinds:** full, half, fence/railing, plus the room separator (UX_PRINCIPLES §3).
- **Finishes ("paint")** on wall sides and room floors (Q-090), no structural materials in this Vision.
- **Snapping defaults** per Q-087; any angle allowed.
- **Crash log + "Report on GitHub" button** (ADR-028).
- **Beginner onboarding:** a starter template + a skippable guided tour (Q-080).
- **Feedback timing plumbing (ADR-025):** commit/settle events exist even before rules do.
- Selection: click, box-select, multi-select.
- Operations: move, copy, duplicate (copy with offset), mirror, rotate, delete, **undo/redo**. Exact semantics are in `EDITING_OPERATIONS.md`.
- Properties panel.
- Save/load JSON with `schemaVersion`.
- Dimensions displayed (wall lengths, opening widths).

Exit criteria:
- [ ] Every operation in `EDITING_OPERATIONS.md` passes its tests, edge cases included.
- [ ] Undo/redo works for every operation, including multi-element ones, as a single step.
- [ ] Save → reload produces an identical model (round-trip test).
- [ ] G-1 usability test done by the owner.

What could go wrong:
- Wall-join geometry eats weeks. (Very likely. Spike A should reduce it.)
- Floating-point drift after repeated mirror/rotate (walls that "should" touch are 0.0000001 mm apart). → integer mm or tolerance strategy (ADR-006).
- Undo bugs from mutable state. → command pattern / immutable model from day 1 (ADR-011).

## Phase 2 — Structural Vision (module) + Tier 0 rule checks

**Goal:** First real feedback, based on **geometric and topological rules** (no force calculations yet), delivered as `module-structural`: one construction-system rule pack (Q-055), BR + EU profiles, a material pack, and a Vision switch. **Review the rule list with the engineer contact before Phase 2 ends (Q-068; ENGINEER_QUESTIONS batches 1–2).**
Also in Phase 2 (ADR-029): notes on elements, protection markers ("load-bearing, don't remove"), the handoff banner, and the Brazil data pack loaded through the pack mechanism (ADR-030), not hard-coded.

Scope:
- Add structural meaning: each wall is `load-bearing | non-load-bearing | unknown` (how this gets decided is ADR-017 — a critical, still-open decision).
- Add minimal "what's above": slab/roof regions with span direction (needed to know which walls carry load).
- Rule engine: rules are pure functions `(model) → findings[]`.
- First rule set (see `STRUCTURAL_ANALYSIS.md` §Tier 0), e.g. opening in bearing wall without lintel, pier too narrow between openings, opening too close to a wall junction, bearing wall removed/moved, wall too slender, etc.
- Findings panel + highlight on canvas.
- **Change impact (diff of findings before/after each command).**

Exit criteria:
- [ ] ≥ 8 Tier-0 rules, each with ID, source (or `UNVERIFIED` tag), and tests.
- [ ] Findings diff works on undo/redo too.
- [ ] Safety wording test (G-8) passes.

What could go wrong:
- Rules depend on thresholds that vary by country and construction system → wrong for the user. (ADR-009)
- Too many warnings → users ignore them ("alarm fatigue"). → severity levels + grouping.
- "Load-bearing or not" is wrong at the input → every downstream rule is wrong. (**Biggest conceptual risk**, R-02.)

## Phase 3 — Materials + Tier 1 simplified calculations

**Goal:** Numbers, not just rules: simplified gravity load path ("load takedown") and lintel checks.

Scope:
- Material library with sourced properties and a **confidence level per value**.
- Loads: self-weight (from material density) + floor/roof loads (live and dead loads, defaults from the chosen code).
- Tributary-area load takedown: slab → walls/beams → down to ground.
- Wall compressive stress vs allowable (simplified).
- Lintel over an opening as a simply supported beam: bending, shear, deflection.
- Show *calculation traces*: the user can expand a finding to see the formula and the numbers used.

Exit criteria:
- [ ] Every formula has ≥ 2 hand-calculated validation cases.
- [ ] A worked example in `STRUCTURAL_ANALYSIS.md` matches the app output to within tolerance.
- [ ] Ideally: one case reviewed by a real engineer (Q-005).

What could go wrong:
- Material values from the internet are wrong or inconsistent (R-04).
- Masonry "arching action" over openings: simple beam formulas over-predict the load on lintels. Do we model it? (Q-033)
- False precision: showing "stress = 0.4372 MPa" suggests more accuracy than exists. → round + show ranges.

What could go wrong: data model rework if ADR-015 chose "single storey only" in a way that hard-codes it. → keep `levelId` in the model from Phase 1 even if there's only one level.
